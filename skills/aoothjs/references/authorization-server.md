# Authorization server (CLI login, service SSO, MCP connectors) — @aooth/auth-moost + @aooth/auth/authz

aoothjs AS an OAuth/OIDC **provider** for its OWN clients — the inbound twin of [federated login](oauth.md). One authorization-code + PKCE flow drives a real interactive login (password/MFA/consent, even mid-flow SSO); the only thing that varies is the injected **client/redirect policy** (+ whether an `id_token` signer is wired). Tier 1 = a CLI on a loopback redirect (access token); Tier 2 = a registered first-party service (`id_token`, "Sign in with the main app"), consumable by the existing [`OidcProvider`](idp.md); MCP connectors = RFC 7591 **self-registered** clients (claude.ai-style: discover via RFC 9728 PRM + RFC 8414 metadata, register — public `"none"` or confidential `"client_secret_post"` — grant, access token + optional rotating `refresh_token` — invariants 14–23; consent-only silent authorize for live sessions — invariant 24). Framework-agnostic parts in `@aooth/auth/authz`; HTTP endpoints in `@aooth/auth-moost`.

## Quick start (Tier 2 — Tier 1 = just `LoopbackClientPolicy`, no signer)

```ts
import {
  CompositeClientPolicy,
  IdTokenSigner,
  LoopbackClientPolicy,
  OidcClaimsResolver,
  RegisteredClientPolicy,
  scopeGrants,
  AuthCodeStoreMemory,
  PendingAuthorizationStoreMemory,
} from "@aooth/auth/authz";
import {
  AuthorizeController,
  CLIENT_REDIRECT_POLICY_TOKEN,
  PENDING_AUTHORIZATION_STORE_TOKEN,
  AUTH_CODE_STORE_TOKEN,
} from "@aooth/auth-moost";
import { Controller, Inherit, Inject } from "moost";

const signer = new IdTokenSigner({
  issuer: `${ORIGIN}/auth`,
  kid: "main-1",
  alg: "RS256",
  privateKey: PKCS8_PEM,
  publicKey: SPKI_PEM,
}); // issuer = {origin}/auth, EXACTLY
class Claims extends OidcClaimsResolver {
  async resolveClaims(userId: string, scope?: string) {
    // `u.email` is YOUR model's field — base `UserCredentials` has no `email`
    // (a login-handle email is consumer-declared, tagged `@aooth.user.email`).
    const u = await userService.getUser(userId);
    return scopeGrants(scope, "email") && u.email ? { email: u.email, email_verified: true } : {};
  }
}
const policy = new CompositeClientPolicy({
  loopback: new LoopbackClientPolicy(),
  registered: new RegisteredClientPolicy({
    clients: [
      {
        clientId: "billing-app",
        redirectUris: ["https://billing.example.com/cb"],
        type: "confidential",
        clientSecret: SECRET,
        scopes: ["openid", "email", "profile"],
      },
    ],
  }),
});

// moost@0.6.x does NOT inherit @Inject across `extends` → re-declare the ctor.
@Inherit()
@Controller("auth")
class OidcAuthorize extends AuthorizeController {
  constructor(
    auth: AuthCredential,
    @Inject(CLIENT_REDIRECT_POLICY_TOKEN) p: ClientRedirectPolicy,
    @Inject(PENDING_AUTHORIZATION_STORE_TOKEN) pending: PendingAuthorizationStore,
    @Inject(AUTH_CODE_STORE_TOKEN) codes: AuthCodeStore,
  ) {
    super(auth, p, pending, codes);
  }
  protected override getIdTokenSigner() {
    return signer;
  }
  protected override getOidcClaimsResolver() {
    return new Claims();
  }
}

app.setProvideRegistry(
  createProvideRegistry(
    [AuthCredential, () => authCredential],
    [UserService, () => userService],
    [CLIENT_REDIRECT_POLICY_TOKEN, () => policy],
    [PENDING_AUTHORIZATION_STORE_TOKEN, () => new PendingAuthorizationStoreMemory()],
    [AUTH_CODE_STORE_TOKEN, () => new AuthCodeStoreMemory()],
  ),
);
app.registerControllers(OidcAuthorize); // the SUBCLASS, not the base
```

## Invariants

| #   | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **One flow, three pluggable policies.** Authorization-code + PKCE (S256) + back-channel `/token` is canonical for ALL tiers. Tier 1 = `LoopbackClientPolicy` (any `127.0.0.1`/`[::1]`/`localhost` redirect, any port, public/no `client_id`, PKCE is the binding). Tier 2 = `RegisteredClientPolicy` (static registry; `client_id` + exact-match `redirectUris` allowlist + `public`/`confidential`). DCR = `DynamicClientPolicy` (invariant 14). `CompositeClientPolicy({ loopback, registered?, dynamic? })` dispatches on **presence + OWNERSHIP of `client_id`**: absent → loopback; present → `registered` iff its `hasClient(id)` knows it (static-first — DCR can never shadow a static id), else `dynamic`. `authenticateClient` routes through the SAME picker (presence-based dispatch would 401 every dynamic redemption). ≥1 of registered/dynamic required; both ⇒ `registered.hasClient` required (validated at construction).                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 2   | **Authority is fixed at `/authorize`, never at `/token`.** `policy.resolveClient` decides `tokenPolicy` + `id_token` intent + `aud` + granted `scope` (`requested ∩ allowed`); these are recorded on the `PendingAuthorizationStore` entry and copied onto the issued code. `/token` ONLY verifies PKCE + client auth and mints.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 3   | **Trust gate FIRST.** `authorize` calls `resolveClient` before anything else — until it passes there is no validated `redirect_uri`, so a failure is a benign `400`, never a reflected redirect. Param errors AFTER the gate fail-soft to the validated redirect (`?error=`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 4   | **`id_token` signer + claims resolver are GETTERS, not DI tokens.** An optional `@Inject`/`@Optional` dep PANICS in moost's `resolveMoost` route-table pass (triggered by `AuthController`'s `@MoostInit` refresh-cookie hook → _"Class is not Injectable and not Optional"_). Override `getIdTokenSigner()` / `getOidcClaimsResolver()` on a subclass; a method has nothing to resolve. The mandatory deps (policy + 2 stores) stay on string tokens (always provided → resolve cleanly in that pass).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| 5   | **Register the SUBCLASS, not the base.** The base `AuthorizeController` returns `undefined` signer → `discovery`/`jwks` 404 + `sub`-only tokens. Re-declare the ctor with the SAME three `@Inject` tokens + `super(...)` (moost@0.6.x doesn't inherit `@Inject`/`design:paramtypes` across `extends`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 6   | **Signer `issuer` = `{origin}/auth`, EXACTLY.** A relying `OidcProvider` compares `id_token.iss` / discovery `doc.issuer` for exact string equality (RFC 8414). The signer canonicalises (strips a trailing slash) once so `iss` / `issuer` / derived endpoint URLs are byte-identical. `kid` is stamped in the JWS header AND the JWKS entry.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 7   | **`discovery` derives every endpoint from the signer's `issuer`** (`/authorize`, `/token`, `/jwks`), so a relying party configured with the same `issuer` resolves them automatically. Route is the dot-segment `@Get(".well-known/openid-configuration")` → `/auth/.well-known/openid-configuration` (registers fine in moost).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 8   | **`OidcClaimsResolver` supplies PROFILE claims only** (`email`/`email_verified`/`name`), gated by `scopeGrants(scope, "email"\|"profile")`. The registered claims (`iss`/`aud`/`sub`/`iat`/`exp`/`nonce`) are owned by the controller. Default `NoopOidcClaimsResolver` → `sub`-only. These profile fields come from the CONSUMER's own user model — base `UserCredentials` no longer declares `email` (a login-handle email is a consumer field tagged `@aooth.user.email` — see [recovery-and-handles.md](recovery-and-handles.md)); read whatever columns your model declares.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 9   | **Token-endpoint client binding is symmetric.** A code minted for a registered client MUST be redeemed with the matching `client_id` (+ `client_secret` for confidential — constant-time check); a code minted for a loopback CLI must carry NO `client_id` (a spurious one → `401 invalid_client`). The binding extends to refresh tokens: a family is stamped `metadata.authzClientId` at mint and redeems only for that client (invariant 21). An `id_token` client with no signer wired → `500 server_error` (misconfig, never mint unsigned).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 10  | **Two short-lived stores, abstract + memory + atscript-db.** `PendingAuthorizationStore` (in-flight, keyed by opaque `handle`, ≈ login-session TTL; the handle rides the login-wf ctx and survives an SSO detour) + `AuthCodeStore` (single-use, `consume()` atomic, ≈30–60 s). Multi-pod → swap the durable `PendingAuthorizationStoreAtscriptDb` / `AuthCodeStoreAtscriptDb` (`@aooth/auth/atscript-db`; raw models `@aooth/auth/atscript-db/pending-authorization` + `…/auth-code`) under the same tokens — `tokenPolicy` persists as a JSON string (open `payload` ⇒ not a closed `@db.json`), and `consume` is an atomic `findOne`→`deleteOne` where `deletedCount === 1` is the single-use claim (no version column). The login-wf `mint-authz-code` step resolves them via the `AuthorizeRuntime` DI holder. Each pending row ALSO carries a `binding` secret (the `aooth_authz` cookie value, invariant 13) — a custom durable store MUST round-trip it or the consent gate fails closed.                                                                                                                                                                                                                                                                                                                                                                      |
| 11  | **"The inbound grant and the outbound provider are two ends of the same wire."** A first-party service consumes a Tier-2 deployment with `new OidcProvider({ issuer: "{origin}/auth", clientId, clientSecret })` — zero new client code; the whole federated leg (`beginSso`/`sso-callback`) works unchanged.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 12  | **`redirectPrefixes` is boundary-checked** (URL-normalize to kill `..` traversal + a path boundary after the prefix). Still prefer exact-match `redirectUris` — prefixes only for a tightly-scoped path on a trusted origin.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 13  | **Consent gate + browser binding run BEFORE the mint (built-in, AUTH-SERVER §6 — you wire nothing).** `/auth/authorize` mints a `binding` secret → records it on the pending auth AND drops the `aooth_authz` `httpOnly`/`SameSite=Lax` cookie. The login-wf `authz-consent` step then (1) **constant-time-matches** the cookie vs the stored `binding` — mismatch/absent ⇒ **fail-closed** (no prompt, no code; neutralises an `authz` handle phished into a FOREIGN browser, since the secret only ever lived in the browser that hit `/authorize`), then (2) pauses on `AuthorizeConsentForm` (slot `opts.forms.authzConsent`) for an explicit **Authorize**; **Deny** ⇒ 302 `redirect_uri?error=access_denied`, mints nothing. `mint-authz-code` runs **only** after consent stamps `ctx.authz.approved` — `finishWf` does NOT halt the schema, so this approval gate (not a bare `!!ctx.authz`) is what keeps a deny/binding-fail finish from being clobbered by the mint. `loginPath()` MUST be **same-origin** with `/authorize` (host-scoped cookie won't ride a cross-origin login route ⇒ fail-closed); `Lax` so it survives a "Continue with Google" detour. Exported `AUTHZ_BINDING_COOKIE` / `authzBindingCookieAttrs` (parallel to `OAUTH_CSRF_COOKIE`); override the prompt copy with an `extends AuthorizeConsentForm` (`@aooth/auth-moost/atscript`). |
| 14  | **MCP connectors = `DynamicClientPolicy` over a `DynamicClientStore`.** `new DynamicClientPolicy({ store, tokenPolicy?: { kind: "mcp-session", ttl: 30d }, allowedScopes? })` → the composite's `dynamic` slot. Granted scope = `requested ∩ allowedScopes ∩ registration scope` — NEVER the registration's self-declared `scope` alone (attacker-supplied; it also feeds the consent copy). `https` redirects exact-match; loopback entries are PORT-AGNOSTIC (RFC 8252 — CLI/MCP-inspector clients bind ephemeral ports). Mints an access token only — NO `id_token`. `resolveClient` ALWAYS sets `clientId` on the `ResolvedClient` (the symmetric binding of invariant 9 depends on it); `authenticateClient` = existence re-check, so a GC'd registration fails closed at `/token`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 15  | **RFC 7591 registration = `DynamicClientRegistration` behind `POST {issuer}/register`** (enable via the `getDynamicClientRegistration()` getter override — default `undefined` ⇒ 404 + no `registration_endpoint` advertised). Pipeline: validate → `guard` hook (throw `ClientRegistrationError` to reject; other throws → 500) → lazy GC of NEVER-USED rows (`unusedClientTtlMs`) → reject-when-full `maxClients` cap (NEVER evict used rows — a connector caches its `client_id`; evicting strands it) → mint secret (confidential). Validation NARROWS per RFC 7591 §2: `grant_types`/`response_types` are intersected with supported (`["authorization_code", "refresh_token"]` / `["code"]` — a connector's `refresh_token` ask is registered and ECHOED; the result must still include `authorization_code`, else `invalid_client_metadata`); auth method absent ⇒ `"none"`, and BOTH `"none"` + `"client_secret_post"` are accepted by default (`validation.allowedTokenEndpointAuthMethods: ["none"]` = public-only; an explicit disallowed ask — e.g. `client_secret_basic` — is rejected, never silently downgraded); `client_name` stripped of Cc/Cf (bidi/zero-width consent-spoof defense), capped. 201 carries `client_id_issued_at` in SECONDS. Request must be `application/json`.                                                                    |
| 16  | **RFC 8414 metadata is SIGNER-INDEPENDENT.** `GET {issuer}/.well-known/oauth-authorization-server` needs only `getIssuer()` (default = signer's issuer; a signer-less deployment MUST override it — NEVER derive from the Host header: the doc is cacheable, that's an injection vector). 404 only when neither. Advertises `registration_endpoint` iff DCR wired (and so does `openid-configuration` in a combined signer+DCR deployment); `jwks_uri` iff signer; `scopesSupported()` getter feeds `scopes_supported`. `openid-configuration` stays signer-gated (404 without signer) — unchanged for Tier 2.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 17  | **Two documents MUST be mounted at the HTTP-server ROOT by the consumer** (a prefix-mounted controller can't): the RFC 8414 path-insertion form `/.well-known/oauth-authorization-server/<issuer-path>` and the RFC 9728 PRM `/.well-known/oauth-protected-resource`. Build them from the exported `buildAuthorizationServerMetadata` / `buildProtectedResourceMetadata` (re-exported by `@aooth/auth-moost`) with the SAME issuer → byte-identical to the controller's suffix form. The resource server's 401 carries `WWW-Authenticate: buildWwwAuthenticateBearerChallenge({ resourceMetadataUrl })` — that header is what starts the whole connector discovery. Values are sanitized (controls stripped, quotes escaped) — header-injection safe.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 18  | **RFC 8707 `resource`: record + consistency, NO audience enforcement (v1).** `/authorize` records a single value on the pending auth (copied to the code); presence never errors, but a REPEATED param or >2000 chars fails soft `error=invalid_target` — `@Query` silently yields the FIRST occurrence of a repeated param, so multiplicity is probed via `useUrlParams().params().getAll()` (reusable moost gotcha). `/token`: both legs present and different → `400 invalid_target`; one-sided presence accepted. `invalid_target` is in `AuthorizeErrorCode`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 19  | **Consent renders the dynamic client HONESTLY (no bypass).** The same `authz-consent` + binding gate (invariant 13) runs for DCR clients. `authz-consent` stages `clientName = req.clientName ?? req.clientId` + `redirectHost` (parsed from the VALIDATED redirect — the trustworthy identity a self-chosen name can't fake); `AuthorizeConsentForm` shows "“Name” (host) wants to sign in…". The paragraph renders as a TEXT node (`AsParagraph` uses `toDisplayString`) — attacker `client_name` can't become markup/links; registration-time sanitization is defense-in-depth.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 20  | **Connector token lifecycle: pair a short access ttl with `refresh` (invariant 21); still no RFC 7009.** Without `tokenPolicy.refresh` the grant is a plain long-lived bearer and the connector re-runs authorize+consent at expiry. Pick a dedicated `kind` (`mcp-session`) so grants surface in `listSessions(userId, { kind })` — the sessions API is the revocation path (kills the whole family, refresh included). Durable store = `DynamicClientStoreAtscriptDb` (model `@aooth/auth/atscript-db/dynamic-client`; `redirectUris`/`grantTypes`/`responseTypes` are JSON-string columns; `clientSecretHash` for confidential rows) under `DYNAMIC_CLIENT_STORE_TOKEN` — the BASE controller never injects it (optional-@Inject panic, invariant 4); a DCR subclass adds it as a REQUIRED ctor param. MIGRATION: pending/code models gained nullable `clientName`/`resource` — syncSchema BEFORE connector traffic (connectors ALWAYS send `resource`; un-synced column fails the `/authorize` insert). The `/authorize` trust-gate 400 body is generic — with DCR, `invalid_client` vs `invalid_redirect` is a client_id-existence oracle.                                                                                                                                                                                                                        |

| 21 | **OAuth 2.1 `refresh_token` grant — opt-in per `TokenPolicy.refresh`, client-bound, fixed ceiling.** `tokenPolicy: { kind, ttl: <short>, refresh: { ttl?: <grant lifetime>, graceMs?: <rotation grace, ms> } }` (default `DEFAULT_AUTHZ_REFRESH_TTL_MS` = 30d, deliberately independent of the session tier's posture) makes `/token` pair the access token with a rotating `refresh_token`; `POST /auth/token { grant_type: "refresh_token", refresh_token, client_id, client_secret? }` redeems it — `{ token_type, access_token, expires_in, refresh_token, userId }`, JSON body, no cookies. Rules: (a) client-bound ONLY — the family is stamped `metadata.authzClientId`; clientless loopback grants IGNORE `refresh`; a browser-session refresh token (no stamp) or another client's ⇒ `400 invalid_grant` with the family UNTOUCHED (binding checked before any rotation); (b) one-time-use rotation with a FIXED ceiling — the family carries `metadata.refreshRotation: "always"`, which wins over an instance `'sliding'` config, so rotation never extends the grant; (c) a grace window (30s default; the policy's `graceMs` — stamped `metadata.rotationGraceMs` — wins over the instance `rotationGraceMs`, `0` = strict) tolerates a benign re-presentation of the just-rotated token by IDEMPOTENTLY re-delivering the SAME pair (a connector whose rotation response died with a redeploy retries and recovers instead of bricking — size `graceMs` 30–60s to the redeploy window); replay beyond it — or of a superseded token — REVOKES the whole family (`invalid_grant`); (d) authority never widens — `kind`/`payload`/access `ttl` (stamped `metadata.accessTtl`) ride the family. Confidential clients present `client_secret` on refresh too. Errors: no token → `400 invalid_request`; missing/unauthenticated client → `401 invalid_client`; everything else → `400 invalid_grant`. Metadata + DCR tell the truth: `grant_types_supported: ["authorization_code", "refresh_token"]` in the builder + both discovery docs. Non-moost token endpoints: use `tokenPolicyToIssueOptions(policy, clientId)` — it applies ALL of (a)'s rules; see [refresh.md](refresh.md) for the session-layer seams (`IssueOptions.refresh`, `refresh(token, { guard })`, `RefreshResult`). |
| 22 | **Two deployment pitfalls (observed against real claude.ai traffic).** (a) Connectors ALSO resolve both `/.well-known/oauth-*` documents at the BARE ORIGIN, ignoring the issuer's path — an SPA catch-all answering `200 text/html` there poisons the client (it parses HTML as metadata) and the handshake aborts client-side with no server error. Serve both root aliases (same builders + issuer as invariant 17) and hard-404 every other `/.well-known/*` before the catch-all. (b) CORS: browser-based MCP clients (inspector-class) run discovery/DCR/token from the page — the metadata endpoints, `/register`, and `/token` need `Access-Control-Allow-Origin: *` + OPTIONS preflights. `*` is correct there (public, credential-free surfaces) and WRONG for the cookie-carrying session endpoints — scope it to the authz paths. |
| 23 | **Confidential DCR (`client_secret_post`) — what claude.ai's platform registers.** `register()` mints a 256-bit secret, stores ONLY its SHA-256 digest (`DynamicClient.clientSecretHash`), and returns the plaintext ONCE (`RegisteredDynamicClient.clientSecret` + `clientSecretExpiresAt: 0` — the controller echoes `client_secret` + `client_secret_expires_at: 0` per RFC 7591 §3.2.1). `DynamicClientPolicy.authenticateClient` then constant-time-verifies the posted secret on EVERY token-endpoint call (both grants); missing/wrong ⇒ `401 invalid_client`. Public `"none"` clients keep PKCE-only — a spurious secret is ignored. Helpers: `mintClientSecret` / `hashClientSecret` / `verifyClientSecret` from `@aooth/auth/authz`. |
| 24 | **Consent-only authorize (live session → consent, no credentials form) — OPT-IN.** Override `resolveAuthzReauthPolicy(ctx)` on the `AuthWorkflow` subclass to `{ mode: 'consent-only' }` (default `'always-reauth'` = today's re-type-password behavior; type `AuthzReauthPolicy` from `@aooth/auth-moost`). `init-login` then probes the trigger request's auth context on authz STARTs (never the federated re-entry): a valid session binds `ctx.subject` + `ctx.authz.silent`, skips `credentials` AND the MFA loop (pre-set `otp.verified`; keep the loop with `requireMfa: true`), and pauses straight on `AuthorizeConsentForm`, which names the acting identity ("Signed in as …" via `public.authz.signedInAs`). EVERY probe failure (no/expired/garbage credential, deleted/locked/inactive account — the account-state gate runs BEFORE the bind) falls back silently to the credentials path. `maxSessionAgeMs` = freshness ceiling against the SESSION ORIGIN (`SessionInfo.createdAt`; origin-less legacy tokens = stale). Silent runs skip `record-login` (no `lastLogin`, no `afterLogin`, no `isFirstLogin` steps) but hygiene gates (channel enrolment, terms) still apply, seeded from the row. PRECONDITION: the flow trigger route must SEE the session credential (same-origin cookie, or the SPA replays the bearer on triggers) and the auth guard must be mounted on it — otherwise the flip is a silent no-op. Browser binding (invariant 19/§consent-gate) is checked BEFORE any prompt, so a phished handle stays inert even in a session-holding browser. |
