# upgrading

Load when bumping `@aooth/*`, when an app "worked before" an upgrade, or when writing code against an older aooth. All `@aooth/*` packages share one version — bump them together, with the matching ecosystem line ([ecosystem.md](./ecosystem.md) § Peer dependencies).

## 0.2.24 — invite link dies once the password is set; re-issue starts over; consent dead end fixed; a lapsed lock starts the failed count over

- **SECURITY — invite:** the emailed link could still act after the invitee set the password (durable `store`: continued the run → MFA of the holder's choosing, auto-login; encapsulated `store`: reopened the password form and OVERWROTE the password — docs claimed "refused"). Now the password submit claims the invite (`UserService.claimInvitation`: password + new marker in ONE CAS): the run continues only in that browser (durable: under a FRESH `wfs`), the emailed link → durable `410 WF_EXPIRED` / encapsulated `410 INVITE_LINK_USED` (new code — add to SPA branches + translations); two holders at the form → first wins; later pauses expire at min(default, link expiry) (were unbounded under the encapsulated default); before the password nothing changes. `GET /auth/invite/post-redemption?uid=` → "link already used" envelope for pending-with-password (was 404); `peekInvite` → `null` for used links and past-password run tokens; an encapsulated link reopened after the run FINISHED → `410 INVITE_LINK_USED` (was the "already accepted" envelope). Clients: send the latest `wfs`; invite page `<AsWfForm persist-token="session" @link-used="dropLink">` (`@atscript/vue-wf` 0.1.187) — token per tab in `sessionStorage`, never URL/history. Legacy runs paused past the password before the upgrade: the emailed link continues until done / TTL ([invites.md](./invites.md) #17). Issuer run already on `store` (registry `default: "store"`, or an app swap before `send-email`) + `@wooksjs/event-wf` ≤ 0.8.5 → the email carried the ISSUER's own token (issuer's page could open the invitee's form) → fixed by `@wooksjs/event-wf` 0.8.6 / `@moostjs/event-wf` 0.7.10 (out-of-band pause = always a fresh handle) — bump the peers. Bundled registry and magic links were never affected.
- **`@wooksjs/event-wf` 0.8.6: `swapStrategy()` / `useWfStrategy()` THROW outside a workflow run** → app code / tests calling `AuthWorkflow` step methods directly (e.g. `ssoCallback` in an HTTP test context) now fail; drive them through a flow request (`POST /auth/trigger`) instead.
- **Re-issue starts over:** re-invite / resend of a pending invite whose link already set a password resets it in the same CAS (`refreshInvitation`): random initial password, no MFA, no trusted devices, no `verifiedEmail`; invite `promote-to-handle` moved after acceptance; NOT reset: username, consents, your columns, `extra-step` writes → the invitee sets a password (and MFA) again; earlier run → `410 INVITE_REPLACED`, its writes never land (CAS on the marker) ([invites.md](./invites.md) #18).
- **Fix — MFA lockout:** a correct password no longer resets `failedLoginAttempts` while a second factor is due (`login()` keeps it; `verifyMfa` success / `record-login` reset it) — was: `threshold - 1` TOTP guesses per password entry. Own second factor after `login()` → call `recordLogin(id)`.
- **Fix — consents:** a missing required consent on the set-password form (invite, forced change, recovery) re-pauses BEFORE the password is written (was: written, then the corrected submit → `410 PASSWORD_CHANGED_SIGN_IN_AGAIN`, an invite dead end).
- **Lockout:** when a timed lock lapses, `account.failedLoginAttempts` restarts at 0 — the failure that finds the lapsed lock is the 1st of a new `threshold` (was: count kept → every wrong password after the first lock re-locked for another `duration` until a successful sign-in; one request per period kept an account locked). Every timed lock (tripped, or `lockAccount` with a duration), every lift site (`login`, `verifyMfa`, `assertCanSignIn`, and the no-password account-state gate of `sso-callback` / silent authorize / `prove-control` — which refused a lapsed lock before). Permanent (`lockEnds: 0`) unaffected. Online guess rate after the first lock: `threshold` per lock period (was 1) — keep the route rate limit. `AuthWorkflow.isAccountBlocked` is now `Promise<boolean>` — overrides `async`, callers `await`: `super.isAccountBlocked(u) && extra` un-awaited = `extra` → the base check is SKIPPED (locked / inactive pass); write `(await super.isAccountBlocked(u)) || extra`. The lift is a `withCas` write (custom `UserStore`: nothing to do). `'uniform'` shadow count restarts the same way — a custom `lockoutShadowStore` needs `reset` (bundled stores have it), else unknown handles re-lock on the first failure after a lapse. No app change; update tests expecting the re-lock ([user-service.md](./user-service.md)).

## 0.2.21 — invite link keeps its 7 days until the password; recovery retries keep their window; send limits use the app-wide 429 message

- **Invite:** every accept-phase pause BEFORE the password is set (username pick, password form, their retries) now expires exactly at the emailed link's expiry (issue + `send-email`'s `@StepTTL`, 7 days; recorded as `ctx.admin.linkExpiresAt`), whatever the store `defaultTtl` — short (was: cut to it on open), long or none (was: lived on without end); `peekInvite` `expiresAt` stays the same across opens. AFTER the password (MFA enrolment, `extra-step`): with a durable `store` the same link continues the run under the store default (unchanged) — no `defaultTtl` = until the run finishes → set a `defaultTtl` on the durable store (recommended; no code change required); with the encapsulated `store` the emailed token restarts at the password form, which is refused. Pre-0.2.21 invites (no `linkExpiresAt`) behave as before. No app change ([invites.md](./invites.md) #14).
- **Recovery:** each step (picker, code form — again after a resend —, password form — also after a magic link) still gets a fresh `recoveryStateTtlMs` from when it is shown (unchanged; re-posting a step without form data = shown afresh → the window is an idle timeout, not a hard cap). NEW: retries keep that window (`ctx.recoveryStepExpiresAt`) — before, a wrong code / resend wait / refused password / invalid pick fell to the store default (never without one) and a submitted-but-invalid form RESTARTED the window. Pre-0.2.21 paused runs: a retry gets a fresh, recorded window. A custom recovery step that first shows itself without `resolveInput()` → call `stampRecoveryExpiry(err)` on that pause, else it continues the previous step's window.
- An app `@StepTTL` on `choose-username` / `create-password-form` / `pincode-check` / `select-recovery-mode` does NOT change the pauses these flows stamp themselves (new in 0.2.21: invite pauses before the password + recovery retries; recovery first displays were already stamped).
- Fix: default invite delivery (`'outlet-email'`) now passes the link's lifetime to the email outlet (`expiresAtMs` = the `send-email` `@StepTTL`, 7 days) — apps that set `magicLinkTtlMs` sent invite emails with THAT expiry before.
- Fix: `rateLimitInterceptors({ message })` now also words the in-workflow `aooth.send` / `aooth.send-user` 429s (were the built-in text) — apps setting an app-wide `message` see it there too; a rule message through `policies` still wins ([rate-limit.md](./rate-limit.md) #12).

## 0.2.19 — trusted devices dropped on password change; locking default; `aooth.trigger`; invite resend; password form min length

- **Password change drops trusted devices:** `UserService.changePassword` / `setPassword` empty `trustedDevices` in the same write (recovery, change-password, forced change, admin reset) → each remembered device does MFA once more. A forced change at sign-in runs BEFORE that sign-in's MFA → the device is asked in that same run (re-remembering there works). Delete app-side `trustedDevices` clean-up after resets. [user-service.md](./user-service.md).
- **Lockout on by default:** `UserService` WITHOUT `lockout` → `{ threshold: 10, duration: 15 min }` (was never locking); password + TOTP failures share the count; `lockoutDisclosure: 'uniform'` (default) now shadow-locks unknown handles too (share `lockoutShadowStore` across instances). A passed `lockout` object keeps today's field defaults (`0`); opt out = `lockout: { threshold: 0 }`. COUNTS: sign-in passwords, wrong TOTP (incl. manage-MFA step-up), federated link password proof, any app `UserService.login()` / `verifyMfa()`. `resolveLockout` → `admin-only` / `self-service` without a `UserService` lockout = PERMANENT locks after 10 failures now. `failedLoginAttempts` reset only on a successful sign-in / correct TOTP / `unlockAccount` in 0.2.19–0.2.23 (a lapsed lock kept the count → each further wrong password re-locked; since 0.2.24 the count restarts at the lapse); accounts with ≥ 9 stale failures lock on their next failure. Recovery does NOT lift a `temporary` lock (opts: `resolveLockout` → `self-service` = reset lifts + zeroes, locks permanent till then; or `users.unlockAccount(ctx.subject)` in `afterPasswordReset`).
- **Trigger routes rate limited:** `POST /auth/trigger` + `/auth/change-password` + `/auth/add-mfa` share bundled `aooth.trigger` `150/5m`, keyed like the other bundled route policies (interceptor `key`, default IP); every step of every bundled flow counts. Re-tune / switch off via `rateLimitInterceptors({ policies: { "aooth.trigger": … } })`. Method-level → it now BEATS app-wide `rules` and a class-level `@RateLimit` on an `AuthController` subclass: a stricter figure set that way silently becomes 150/5m unless moved to `policies`. An override's own method-level `@RateLimit` still REPLACES it; drop an override that only existed to add one. [rate-limit.md](./rate-limit.md) #12.
- **Invites:** new `resend` action (body `{ action: "resend", formData: { email } }`) + `duplicateInviteCheck` verdict `'resend'` (keeps roles/extras/issuer, fresh link; works with `hashHandles`; skips `prepareUser` / `inferAdminRoles` → put resend authorization in `duplicateInviteCheck`; any invite-permission holder can resend any pending invite by default) — replace any "re-send the stored link" code ([invites.md](./invites.md) #15). Kept roles (resend, or a re-invite picking none) must be within the issuer's available roles when the picker is on with a whitelist, else `AOOTH_INVALID_ROLE` (#16). PUBLIC TYPE CHANGE: `InviteForm.roles` is now optional (`roles?: string[]`). A `duplicateInviteCheck` override with a written-out return type that returns `super.duplicateInviteCheck(input)` must add `"resend"` to that type.
- **Forms:** `SetPasswordForm` / `ChangePasswordForm` min length = the `PP_MIN_LENGTH` policy's, else 8 (fixed `@expect.minLength 8` gone; ONLY the `PP_MIN_LENGTH` code moves it — a custom-coded length rule keeps the floor 8 in the bundled flows, direct `UserService.setPassword` has no floor; the `MIN_LENGTH` validator code no longer applies to these fields — translate `"Password must be at least {min} characters long"` (browser) and `PP_MIN_LENGTH` (server)); `EmailIdentifierForm` description is now "Enter your account email and we will send you instructions to reset your password." (retranslate); `InviteForm.roles` declared `multiselect` (as rendered).
- Docs only: the interceptor `key` never reached `aooth.send` / one-time-code counters — they key on `getIp()`; behind a proxy set `trustProxy` ([rate-limit.md](./rate-limit.md) #6).

## 0.2.4 — insert read-back; reads under write handlers 403

**Breaking:** on an ARBAC DB controller, a read (`this.getOne/getOneComposite/query/pages/geo`) inside an `insert` / `update` / `replace` / `remove` / `removeComposite` override → **403** (it used to run under the WRITE grant; the 403 comes after the committed write). Migration: `await super.update(payload); return readBackUnderReadGrant(id, () => this.getOne(String(id), ""))` — the read grant on the `/one` handler; `undefined` when not allowed.

Additive: `returnRepresentation()` → `true` on an `AsArbacDbController` subclass: `POST /` + `Prefer: return=representation` answers `row` = what `GET /one/:id` answers the caller (READ grant, not the insert grant). Default off. See [db-controllers.md](./db-controllers.md) § Protected hook table.
